# 简历用 · 项目描述

> 本文用于简历/面试讲述，**所有数字均为实测**（证据见 `ROADMAP.md` 与 `eval/*.json`）。
> 规模：业务代码 **7,416 行 / 48 文件**，评测与验证代码 **11,999 行 / 81 文件**
>（另根目录 `scripts/` 1,166 行 / 4 文件）—— **评测代码量超过业务代码**，这是本项目的显著特征。

---

## 一句话概述

**技术资料 Copilot（TechDocs Copilot）**：面向研发/运维的多源技术资料问答——论文、官方文档、
产品手册统一入库 → 混合检索（稠密 + BM25 / RRF 融合）→ **四道 LLM 判分闸门**
（路由 / 相关性 / 幻觉 / 问题匹配）→ 引用校验与拒答 → FastAPI + SSE 服务化。

> 对外定位是“技术资料 Copilot”；底层是可复用的通用 RAG 底座，代码与接口不变。

## 核心亮点（5 点）

### 亮点 1 · 定位并修复「成本不可见」，随后**降本 40%**

**问题**：生产监控里的 token 消耗与直觉严重不符。

**过程**：逐层排查（三层链路，用 5 个探针逐个证伪假设）后定位到根因 ——
**最大的 LLM 调用方（文档判分，36 次/题、占总调用数 90%）的 token 完全没有被统计**，
因为埋点配置在 `ThreadPoolExecutor` 内部**静默失效**（LangChain 的 config 靠
contextvar 传递，而**线程池不继承它** —— 用三条对照实验证实：无线程池 token=11、
线程池不传 config token=0、线程池显式传 token=22）。

**结果**：

| 项 | 修复前 | 修复后 |
|---|---|---|
| 可见 token | 9,898 | **41,868**（**真实成本是可见值的 4.2 倍**） |
| 判分 token | — | **占真实成本 76%** |
| 批量判分后 | — | **173,265 → 104,378（省 40%）**，调用 215 → 30 次 |
| 端到端耗时 | **7.2s**（逐块基线） | **3.8 ~ 5.4s**（批间并发，判分阶段 3.83s → 1.20s，降 74%） |

**关键取舍**：批量判分把「逐块调用」改为「一次判 8 块」，**块内容一字未改**，
只省掉「被重复发送 36 遍的 system prompt + 问题」。
实测一致率 **91.6%（197/215）**；分歧集中在噪声块，**未造成 golden 块丢失**
（逐块核对见 ROADMAP 4.23.3）。

### 亮点 2 · 检索质量提升：context_recall **0.7492 → 0.8664**

新语料（18 文件 / 523 块 / 3 集合）首测 recall 仅 0.7492。经四轮定位修复：

| 措施 | 效果 |
|---|---|
| 同表多形态副本合并（表格父子块实测否决后的替代方案） | 0.7993 → **0.8501** |
| **发现「配额截断」**（`per_k` 配置改了但**未生效**，因 pydantic 字段默认值在类定义时固定） | — |
| 采纳 `PER_COLLECTION_K=12 / FINAL_K=36` | → **0.8664** |

**验证严格性**：判分口径**补充「判分异常数」统计**后重跑，异常 0 次、干净口径与含保守保留完全一致
（`49/49 · 56/56 · 62/62`），确认「多保留的 golden」是**判分放宽**而非失败兜底。

### 亮点 3 · 自建评测与门禁体系（**评测代码量超过业务代码**）

| 项 | 数量 |
|---|---|
| 评测/验证代码 | **81 个 `.py` / 11,999 行**（评测、探针、测量、验证与对比） |
| 回归门禁 | **19/19 通过**（含 API+SSE、多租户联动） |
| 质量门禁 | **PASS** —— recall 0.8664 · hit_rate 0.9375 · **faithfulness 1.0000** · answer_relevancy 0.8750 |
| golden 集 | 32 题（含「跨行比较」等题型标注） |

**关键设计**：**确定性指标与 LLM 指标分离**（检索层用块 ID 比对，可复现；生成层用判定缓存消除抖动）——
并把被论证「口径失真」的 `context_precision` **移出告警集合**（不再刷告警），
但**仍保留 0.03 的硬门禁**（低于它依然判 FAIL）—— 口径失真的是「告警阈值」，不是「底线」。

### 亮点 4 · 用实测**否决了 4 项「看起来应该做」的改造**

这是本项目最有区分度的部分 —— **每次都先量、再决定，避免了几次高成本的无用改造**：

| 候选改造 | 实测结论 |
|---|---|
| **接入 reranker**（bge-reranker-v2-m3） | **增益 0** —— 8 题无一提升；**天花板本就只剩 9%**（基线已拿到 91%）。**且发现它换进来的是噪声而非 golden** |
| **表格父子块**（schema 重建） | 对「查询类」问题**无增益**（切片已够） |
| **相似度门槛过滤** | 实测**反而伤害召回** |
| **「判分误杀」修复** | 追查后是 **golden 标错**（模型行为正确）—— **本会话出现两次** |

**代价**：其中 reranker 一项，若直接上 GPU + 改检索器，会是数十小时的工作量。

### 亮点 5 · 系统性修正「测量工具本身的缺陷」（10 例，含一次自我更正）

**核心认知**：**错误的测量工具会静静地给出看似合理的错误结论** ——
不报错、不假红，只是结论错。项目中识别并修复了 10 类：

```
对照恒真（探针的 handler 从未注册）· 近恒真匹配（跨文件也算覆盖）
未统计异常数（把「判分失败」混进「判分通过」）· 证据不记样本（默认 3 题覆盖 6 题）
硬编码对照行（永远「看起来正常」）· 把 LLM 抖动当断言 · 粒度错配（组级定阈值、元素级使用）
二元判读（把「调用失败」当「答不对」）· 缓存 key（经查证无缺陷，**我原先的判断被自己实测证伪**）
```

**其中一次是我自己的错误结论**：曾判断「判定缓存 key 缺字段 = 缺陷」，
实测后（查三个判定函数的真实依赖）发现**它们根本不读 golden 的 answer，缓存设计是正确的** ——
**在 ROADMAP 里把原结论标为「已被推翻」并附验证过程。**

### 亮点 6 · 多轮记忆三层：**为什么「只加轮数」不够**

**问题**：多轮对话的「最近 N 轮原文」和「摘要」有**共同盲区** —— **找不回含具体数值的早期轮次**。

```
第 3 轮：问「TurboPuffer 的 QPS 是多少」-> 答 184.54
第 30 轮：问「刚才那个 QPS 对应的产品叫什么」
    最近 13 轮：第 3 轮已过期           -> 答不了
    摘要      ：只留「讨论过 QPS」       -> 答不了
    ★历史向量检索：按语义召回第 3 轮原文 -> 答得了
```

**做法**：三层各司其职，**互补而非替代**。

| 层 | 覆盖 | 边界 |
|---|---|---|
| 最近 13 轮原文 | 近期指代（「它」「那个」）| 总预算 6,000 字，超出从**最老**的丢、保住最近 |
| 摘要（`state["summary"]`）| 主题脉络 | 500 字；超 26 轮才生成，**只生成一次**（不每轮重算）|
| **历史向量检索 top-3** | **含具体数值的早期轮次** | 独立集合，按 `session_id` 隔离 |

**三个关键取舍**：

1. **提轮数前先算 token 账**：实测 13 轮 = 4,672 字符 ≈ prompt 的 22%（检索上下文 16,182 字符），
   才敢从 3 提到 13 —— 而不是拍脑袋。
2. **放弃「单条截断」改用「总预算」**：`text[:300]` 在答案短时形同虚设、答案长时会把 13 轮
   **每轮都砍残**；总预算则相反 —— 短答案容纳满 13 轮，长答案优雅退化成「只记最近几轮」。
3. **历史写入放图结束后**，不放 `generate` 节点内 —— 否则幻觉重试（`not supported -> generate`）
   会导致**重复入库**。

**结果**：长会话能答「第 20 轮问第 3 轮的数值」；6 小时**滑动** TTL（按 `last_active` 而非
创建时间，避免误删持续 6.5 小时的活跃会话）。

**过程中修掉 4 个只有实测才暴露的坑**：LangGraph 把 `messages` 初始化为 `[]` 导致判据失灵、
`stream()` 返回增量导致累积被覆盖、绕过 flush 包装只写 WAL、`create_collection()` 会 drop 重建
（每轮清空整个历史库）。

## 可讲述的工程决策（面试话题）

1. **为什么用「判分后」而不是「判分前」的块数看成本** —— 判分是**固定容量过滤器**
   （不管给 36 块还是 18 块，都只保留 ~7 块），所以「放大配额」对下游生成层几乎无影响，
   但**对判分成本是线性的**。这个观察直接决定了优化方向。
2. **批量判分的一致率约 92% 为什么可以接受** —— ROADMAP 的逐块核对显示分歧集中在噪声块，
   唯一涉及 golden 的分歧是「批量把逐块误杀的答案块救回来了」；保存的产物为 197/215（91.6%）。
3. **并发是安全的吗** —— 实测 1/2/4/8 墙钟 4.4/4.3/5.9/8.1s，全部成功；
   8 并发开始排队（较 4 并发 +37%）→ **推荐上限 4~6**。
4. **为什么坚持「先量再改」** —— 4 项改造被实测否决，其中一项（reranker）本会是数十小时的工作量。
5. **一次自我更正** —— 对「判定缓存缺陷」的判断被自己实测证伪后，把结论标为「已被推翻」。

## 已知边界（诚实列出）

* **reranker**：**已实现并接入开关**（`RERANK_ENABLED=1` 启用 + 分数门槛），
  但实测增益 0（天花板仅 9%），故**默认关闭** —— 不是「未做」，也不是「否决」；
* **表内跨行聚合**：已用「同表切片合并」解决（检索后拼回完整表再生成，n005 实测 3/3 答对）；
  **跨文档聚合**（比较 A 文档与 B 文档的指标）**仍未做**，需要结构化查询（text-to-SQL）；
* **更高并发（16/32）**：未测（8 已显劣化）；
* **服务层 HTTP 并发**：功能已验证，未做 HTTP 层压测。

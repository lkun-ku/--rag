# 第一部分 · 怎样体现「独立干活 / 看懂 bug / 看出 AI 的问题」

## 一、核心策略：把「我会什么」换成「我排除过什么」

初级候选人讲做了什么功能，高级候选人讲**排除了什么错误路径**。本项目最该讲的三次「否决」：

| 我判断不该做 | 依据 | 讲出来是什么信号 |
|---|---|---|
| **不上 reranker** | 实测 8 题增益 0，且天花板只剩 9% | 「我知道收益边界在哪，不为了技术栈完整而堆料」 |
| **不重建父子块索引** | 先用对照实验证明「切片已够查询类用」 | 「先验证问题存在，再动手；不预设方案」 |
| **批量判分不逐块也行** | 16 个分歧中**仅 1 个涉及 golden，且方向是正向**（把逐块误杀的那块救回来了）| 「我知道我改动的影响半径，并逐一验证」 |

**面试话术模板**：

> 「这个项目里我**没做**的东西比做了的更能说明我的判断，比如 reranker——业内几乎默认要加，但我用 8 题 A/B 实测发现增益为 0，因为基线已经拿到了 91% 的召回，天花板只剩 9%，上 GPU 换索引的收益是零。」

**这一句同时证明三件事**：会设计实验、会读数据、敢否定流行做法。

## 二、独立写代码能力 —— 讲「实验设计」而不是「代码行数」

**不要**说「我写了 10,000 行评测代码」。面试官无法验证行数，也不会因此加分。

**要**说「我怎么设计一个探针证伪一个假设」。这是本项目最硬的素材：

### 代表作：contextvar / 线程池探针

**背景**：判分阶段的 token 统计恒为 0，直觉判断是「LangGraph 没传 config」。写探针验证，三条对照：

```
实验 A：无线程池 + 不传 config  -> token=11   （contextvar 继承，能统计）
实验 B：线程池   + 不传 config  -> token=0    （线程池内失效）★假设被证实
实验 C：线程池   + 显式传 config-> token=22   （显式传递有效）
```

**面试时这样讲**（重点在设计，不在结果）：

> 「我先提了三个假设：模型不返回 usage、LangGraph 不传 config、线程池丢 contextvar。
> 第一个假设我用 SDK 直调就排除了。第二个和第三个我设计成三条对照——
> 关键点是**实验 C**：如果不做 C，我只能说 B 是 0，但**不能区分「线程池丢 contextvar」和「代码根本没写」**。
> C 用显式传参拿到 22，才把根因锁定在隐式继承上。」

**这句话证明什么**：
- **会用对照组分离变量**（不是只跑一次看结果）
- **知道「假设可证伪」**（A/B/C 三组各自排除一种解释）
- **理解 contextvar 与线程池的语义**（这是 Python 并发细节，不是基础语法）

### 加分点：写「能一次跑完、结论自证」的脚本

岗位要求「独立写脚本」——高手的标志是**脚本自带对照和边界**：

```python
# 好的探针长这样（本项目 eval/ 下的统一风格）
def check(name, cond, detail=""):
    if cond: print("  [OK ] %s" % name)
    else:    print("  [FAIL] %s  %s" % (name, detail))
    RESULTS.append((name, cond))

# ... 跑完打印汇总
print("%d/%d 通过" % (...))          # ← 让回归系统能正则解析，否则等于没注册
```

**面试表达**：「我所有验证脚本都遵循一个约定 —— **每条断言都带 `[OK]/[FAIL]` 与细节值，结尾输出 `N/M 通过`**。因为前一个项目里我踩过：测试写了但没注册进 CI，等于没写。」

（这是真事：本项目 4.22 发现 `test_grade_batch` 写过但没注册；后面又一次「注册了但输出格式不匹配正则」，被标成「已运行，无通过率可解析」。**能坦承第二次犯同类错误，比假装一次没错更有说服力**。）

## 三、看懂代码 bug —— 分三层举证，越往上越值钱

面试官问「你怎么 debug」，按这个层次回答：

| 层次 | 特征 | 本项目案例 |
|---|---|---|
| L1 机械错误 | 语法/拼写/未定义 | `_cfg` 未定义（删了赋值保留使用）→ NameError |
| L2 逻辑错误 | 边界、状态、时序 | `final_state.update()` 把累积的 4 条消息覆盖成 2 条 |
| L3 语义/架构错误 | 表面能跑，结论全错 | 缓存 key 缺字段 → 改了配置不生效；golden 标错 → 修「没坏的东西」 |

**只讲 L1 显得像新手；能讲 L3 才像能独立扛模块。**

### L3 案例一：改了配置但「看起来没生效」（最能体现深度）

**现象**：做 A/B 实验，把 `FINAL_K` 从 18 改成 36，检索块数几乎不变，连续三次实验结论都一样。

**普通人的排查**：重读代码、看日志、重启、怀疑数据。

**实际的根因**（`tools/retriever_tools.py` docstring）：

> `MultiCollectionRetriever` 的 `per_collection_k`/`final_k` 是 **pydantic 字段**，其默认值在**类定义时**求值并固定。而构造函数**没有传**这两个参数，于是改模块常量对它**完全无效**——它永远用类定义时的值。

**讲出来的方式**：

> 「我一开始也以为是我改的位置不对。但第三次 A/B 结果一样时，我意识到不是「配置没生效」而是「这个字段根本不读运行时值」。
> pydantic 的 `Field(default=...)` 是类属性，编译期就固定了。最后改成显式传参才生效。
> **这个 bug 最阴的地方：它不报错、不告警，只是让三个实验的结论全部失真**——如果我没注意到，会基于错误数据做技术选型。」

**为什么这条加分**：它证明你懂「框架内部机制」（pydantic 类属性求值时机），而且**能意识到自己之前的数据不可信**（元认知）。

### L3 案例二：测试全绿，但线上路径根本是断的

**现象**：修了一个节点后回归 10/10 全绿，但用户提问直接 500。

**根因**：`grade_generation` 里 `_cfg` 未定义 —— **只有端到端跑图才会触发**，而当时 10 项回归里**没有任何一项走完整链路**。

**讲法**：

> 「项目当时有 71 个模块级用例、11 项回归，全绿。但它们是「单函数/单模块」级别的，**没有一项真的把整张图跑一遍**。
> 我加了一个 `test_pipeline_smoke.py`，只跑一题、约 5 秒，补上这一层覆盖。
> 现在回归里有 13 项，其中 2 项是端到端。」

**加一句总结**（这是杀手锏）：

> 「**这次教训让我改了后续所有判断：只要是没有「端到端」那一层的测试，我默认它测不到真实链路。**」

面试官要的就是这种**从一次 bug 提炼出可复用检查项**的能力。

## 四、看出 AI 写出的代码有问题 —— 这是最强的差异化

**大多数候选人和 AI 的协作方式是「让它写，我改改」**。你必须讲出**你怎么审它**。

### 四个可复用的审查手法（按本项目的真实案例讲）

#### 手法 1：对结论要证据，不信「应该可以」

**案例**：AI 建议加 `bge-reranker-v2-m3`（这是 RAG 标配），说「通常能显著提升」。

**我的处理**：先看基线天花板，再跑 A/B。

```
8 题逐题对比：reranker 前后
  提升 0 题 / 下降 0 题 / 完全一致 8 题
  基线已拿到 91% 的召回，天花板只剩 9%
```

**结论**：**否决**。并写进 ROADMAP 的理由是「无法证明有效，且引入 GPU 依赖和 2.5s/题的延迟」。

**面试表达**：

> 「AI 的强项是给出**常规解**，弱项是判断**这个项目的这个阶段需不需要**。
> 我的审法：让数据说话。reranker 是标准件，但我们的召回已经 91%，它最多修 9%，
> 还得付 GPU 和延迟的代价——**技术正确 ≠ 现在该做**。」

#### 手法 2：危险操作必须 dry-run，看样本再 apply

**案例**：AI 生成一个正则批量替换脚本，要把文档里 169 处日期删掉。AI 说「规则保守，安全」。

**我的处理**：先 dry-run 看样本。**三次才发现问题**：

| 版本 | 规则 | 后果（dry-run 显示） |
|---|---|---|
| v1 | `[ \t]{2,} → " "` 压缩空格 | **会改动 13,752 行**——把目录树、表格对齐全压扁 |
| v2 | `[（(]\s*[)）] → ""` 删空括号 | 会删掉**函数调用的空参数列表**：`def f():` → `def f:` |
| v3 | `[，,]\s*[。.] → "。"` | 把 `, ...` 变成 `。..` |
| v4 | 只删日期本身 | 165 行 ✅ |

**面试表达**：

> 「我把「批量替换」当成危险操作，**改成一条正则就先看 10 条样例**。
> 结果前三个版本都会造成大面积破坏——尤其是第二个，它会改坏 Python 语法但**脚本本身不报错**。
> 最后我只保留「删日期」这一件事，**任何顺手清理都不做**。
>
> 这条经验我后来固化成原则：**正则越界一次，就要回退全部，不要「再补一条规则去修上一条」**。」

#### 手法 3：AI 说「这是 bug」时，也要验证是不是它错了

**案例（反向，更重要）**：AI 断言「`JudgeCache` 的 key 缺字段，会导致改了 golden 不生效——这是会静默误导决策的缺陷」。

前一次我信了，写进 ROADMAP 说要修。

**后来自己验证**：去看那三个判定函数**实际依赖什么**：

| 函数 | 实际调用 | 用 golden 的 answer 吗 |
|---|---|---|
| `judge_faithfulness(q, gen, ctx)` | `hallucination_grader_chain(documents=ctx, generation=gen)` | **不用** |
| `judge_answer_relevancy(q, gen)` | `answer_grader_chain(question=q, generation=gen)` | **不用** |
| `generate_answer(q, docs)` | `generate(state)` | **不用** |

**结论**：**key 是 `(kind, question, generation, contexts)`，恰好覆盖了各自的真实依赖 —— 缓存设计是正确的，AI 错了。**

**面试表达**（这段最能体现独立判断）：

> 「我当时的判断错了，而且错在**我看到「命中率高」就直接推断「key 缺了东西」，没去看那个判定到底依不依赖它**。
> 验证只花了查三个函数签名的时间。我把这个更正写回了文档，标成「已被推翻」并附上排查过程。
>
> **我的原则：AI 说「这是问题」和 AI 说「这没问题」，我都要证据。** 区别只在前者容易被我当效率，后者容易被我当安全区——后者更危险。」

#### 手法 4：让 AI 做「我验证过的事」，而不是「我做不到的事」

**分工原则**（讲出来会显得很有方法论）：

```
AI 适合：按既定规则批量生成、给出常规方案、写样板代码、解释陌生 API
我适合：设计对照实验、判断要不要做、审查边界条件、决定取舍

危险区：AI 给结论我不验证（reranker / dry-run 两次教训）
高效区：我给出实验设计，AI 写实现，我验收（33 个脚本都这么做）
```

**具体例子**：记忆模块的两个坑都是这么发现的：

| 坑 | AI 的实现 | 我发现的问题 |
|---|---|---|
| 判据失效 | `has_memory = state.get("messages") is not None` | LangGraph 会把 TypedDict 的 `messages` **初始化为 `[]` 而不是 None** → 判据恒真，单轮也写历史 |
| 值被覆盖 | `final_state.update(value)` 拼 `stream()` 输出 | `stream()` 返回的是**节点增量**，reducer 累积的 4 条会被 `update()` 覆盖成 2 条 |

**面试表达**：

> 「这两个 bug AI 自己写的时候是「符合直觉」的写法，但都有前提假设没验证。
> 我各写了一个最小复现（不调 LLM、几秒跑完）来确认，而不是在完整链路上瞎试——
> **最小复现的价值是把「模型发挥」和「机制问题」分开**。」

## 五、控场建议（面试时怎么讲）

### 30 秒自我介绍（讲出你的定位）

> 「我做的 RAG 知识库项目，业务代码 6 千行，但评测代码有 1 万行——比业务还多。
> 因为我把这个项目的重心放在「**先让事实可见，再谈优化**」：
> 所有结论都以实测数据为依据，也因此**否决过三个「行业标配」的方案**（reranker、父子块索引、提高相似度门槛）。
> 最近刚补上多轮记忆，过程中发现并修掉了两个隐式假设的坑。」

（三个数字 + 一个定位 + 一次最新工作，比罗列技术栈有信息量。）

### 被问「你和 AI 怎么协作」时的三段式

1. **分工**：我做设计与验证，AI 做实现与样板 —— 一句话说完，不神化也不贬低。
2. **我的验收手段**：dry-run 看样本、对照实验分离变量、最小复现定位。
3. **一个具体案例**（dry-run 拦下 13,752 行，或 reranker 否决）—— 一定要有数字。

### 绝不要说的话

| ❌ 别说 | 为什么 |
|---|---|
| 「AI 写的，我 review 过」 | review 是关键词，但你讲不出 review 发现了什么就是空的 |
| 「我按最佳实践做了 RAG」 | 最佳实践 = 没有自己的判断 |
| 「召回率提升了 20%」 | 答不出「从多少到多少、怎么测的、样本多少」就完了 |
| 「我熟悉 LangChain」 | 换成「我用 LangGraph 编排了 5 节点 3 条件边的图，踩过 config 透传三个坑」 |

# 第二部分 · 技术问题与参考答案

## A. 项目架构与选型

### A1. 介绍一下这个项目？为什么用 RAG 而不是微调？

**参考答**：

> 企业知识库问答，把内部文档切块向量化，提问时检索相关片段，让模型基于片段作答。
>
> 选 RAG 有三个具体理由：① **数据更新频繁**，微调要重训，RAG 只要重灌文档；
> ② **要可追溯**，企业场景必须给出「答案来自哪份文档第几段」，微调做不到；
> ③ **成本**，微调一次训练 + 后续推理都贵，RAG 的边际成本是几次检索。
>
> 项目现在的形态：**3 集合 / 18 文件 / 523 块**，1024 维 bge-large，Milvus 3.0.1 Standalone（客户端 pymilvus 3.0.2），
> 生成用 DeepSeek，编排用 LangGraph。

### A2. 为什么用 Milvus？数据量这么小，为什么不直接用 Faiss 或 SQLite？

**参考答**（体现取舍）：

> 当时的判断依据不是「哪个牛」，而是**未来 6 个月的形态**：
>
> | 维度 | 本项目需要 |
> |---|---|
> | 混合检索 | 要稠密 + BM25 稀疏双路，Faiss 只做稠密 |
> | 多进程写入 | 入库是多进程管道，Faiss 是单文件、无并发写 |
> | 服务化 | 要独立服务进程访问，SQLite 嵌入式不合适 |
> | 元数据过滤 | 要按 filename/category 过滤，Faiss 要自己实现 |
>
> 代价是**运维复杂度**（要 Docker 起 etcd/minio/milvus 三件套）。
> 如果现在重做、只有 500 块、纯本地 CLI，我会选 Faiss——**选型要匹配规模，不是越重越好**。

### A3. 三个入口 `graph2` / `graph1` / `rag_agent` 是什么关系？生产走哪个？

**参考答**（诚实且有判断）：

> 只有 `graph2` 是生产链路：API 的 `/ask` 和 `/ask/stream` 都调 `graph2.graph_2.run_with_trace`。
>
> `graph1` 和 `rag_agent` 是**历史和对照**：`graph1` 是迁移前的简化 ReAct，`rag_agent` 是
> LangChain 1.x 的 `create_agent()` 标准写法。
>
> 坦白说**这两套在生产里是冗余的、没被使用**。保留它们有三个理由：
> ① 迁移时的对照物（证明手写图没偏离框架语义）；② `verify_migration.py` 用**字符串动态导入**
> 它们做拓扑断言；③ `rag_agent` 有 SqliteSaver 记忆，是 `graph2` 后来补记忆时的参照。
>
> **如果现在做精简，`graph1`/`rag_agent` 可以删**，代价是丢掉迁移验证的参照物。

### A4. 分集合的依据是什么？加新领域要重写代码吗？

**参考答**（直接回答「会不会重复造轮子」）：

> 按**语义域**分，不按格式分。`DOC_SOURCES` 是一个**配置列表**，每条定义
> `(源名, 目录, 集合名, 格式, parser, enabled)`，集合列表是**运行时从配置动态发现**的：
>
> ```python
> # tools/retriever_tools.py:245
> for s in DOC_SOURCES:
>     if s.get("enabled") and s.get("collection"): out.append(...)
> ```
>
> 所以**加一个新领域（法务/HR）只需加一条配置**，建目录 + 写一条 dict，零代码改动。
>
> **唯一必须重建集合的硬条件：换 embedding 模型或维度**（集合 schema 绑维度）。
> 另外单块超 6000 字符会入库失败（VARCHAR 限制）——这是表格必须切块的物理原因。

## B. RAG 技术深挖

### B1. 召回率怎么从 0.7492 提到 0.8664 的？

**参考答**（讲过程，不要只报数字）：

> 分四步，每一步都有独立验证：
>
> 1. **同表多切片合并**（0.7993 → 0.8501）：发现同一张表被切成 4 片，检索回来的是碎片
> 2. **定位「配额截断」**：`per_k` 改了但不生效——根因是 pydantic 字段默认值在
>    类定义时固定（见 L3 案例一）
> 3. **采纳 per_k=12 / final_k=36**
> 4. **修正测量口径**：先补统计「判分异常数」，确认异常 0 次，才排除「多保留的 golden 是兜底」
>
> 关键在 2 和 4：**2 是框架机制问题，4 是测量口径问题**——如果不修 4，
> 我会把「判分宽松导致的假性提升」当成真提升。

### B2. chunk 策略怎么定的？为什么不用递归切分？

**参考答**：

> 用**分级切片 + 标题合并**：先把标题和它的正文合并成一个语义单元，再按预算切。
>
> 不用递归切分的原因是**它会切断「标题—正文」的归属**：正文没有标题，
> embedding 出来的语义就缺了上下文（「它很快」 vs「Milvus 的导入速度很快」）。
>
> 表格单独处理：`documents/table_handler.py` 先解析 HTML 表格、归并 rowspan/colspan，
> 再按字节预算切块。**这里有个已知代价**——大表必然被切碎，
> 也正是 n005 那个 bug 的根因（下面 C 部分讲）。

### B3. 混合检索怎么做？RRF 为什么不用分数相加？

**参考答**：

> 稠密（语义）+ BM25（关键词）两路召回，用 RRF 融合：
> `score = Σ 1/(k + rank_i)`，只看**排名**不看绝对分。
>
> 为什么不用分数相加：两路分数**量纲和分布完全不同**（cosine 0-1，BM25 可能几十），
> 直接相加等于让 BM25 主导。RRF 只用排名，天然免疫量纲差异。
>
> 实现上还有个中文坑：**Milvus 服务端必须启用 jieba 分析器**，否则中文 BM25 等于没开。

### B4. 怎么处理幻觉？四道判分闸门是什么？

**参考答**：

> **路由**（该不该查库）→ **文档相关性**（检索到的块和不和问题相关）→
> **幻觉检测**（答案有没有超出资料）→ **问题匹配**（答案是否真的在回答这个问题）。
>
> 关键设计有两条：
>
> ① **引用编号校验放在 LLM 判定之前**，因为它**确定性、零成本、零抖动**——
> 答案引用了不存在的 `[9]` 是最危险的幻觉（让用户以为有依据），
> 比「没有引用」更糟，必须先拦。
>
> ② **拒答单独识别**：资料不足时模型回固定文案「知识库中未找到依据。」，
> 下游用字符串精确识别，**不触发熔断重试**——否则会反复得到同样的拒答，白烧 token。

### B5. 多轮对话现在怎么做的？

**参考答**：

> 三层记忆：`messages` 用 `add_messages` reducer 累积 + `SqliteSaver` 按 `thread_id` 持久化，
> **注入 prompt 的是三层**——最近 **13 轮**原文（总预算 6,000 字）+ 摘要（超 26 轮才生成一次）
> + **历史向量检索 top-3**（唯一能找回「第 3 轮那个 184.54」的一层）。
> 会话级隔离，6 小时**滑动** TTL（`last_active` 而非创建时间）。
>
> 实现过程中修了两个「符合直觉但错」的 bug（见 D 部分）。

### B6. 拒答率 30% 是不是太高了？

**参考答**（用数据讲取舍）：

> 拆开看：库外 2 题 + 库内 30 题。**库外 2 题本来就该拒答**（不该联网编造），
> 库内 30 题里 0 题误拒。
>
> 原来的设计更糟：路由倾向于「一切问题都先查库」，库外题查不到就拒答，
> 拒答率 100%。加了 Tavily 联网降级后，库外题**会联网作答**，
> 30% 里有一部分是「合理降级到联网」。
>
> **我不用一个总数字判断好坏，而是按「库内/库外」拆开**——否则会把
> 「该拒答的拒答了」当成缺陷去修，越修越爱编造。

## C. Debug / 看代码找 bug（岗位核心）

> **面试用法**：以下每题都可以**现场给面试官讲「我怎么会发现它的」**。
> 如果面试官贴代码让你找 bug，用这里的思路：**先想「这段代码的隐含假设是什么」，再找假设失效的场景**。

### C1. 给了你一段调用链代码，你怎么定位 bug？

**参考答**（讲方法论，不是答案）：

> 我分三步，**顺序很重要**：
>
> 1. **先分清「它假设了什么」**：每个函数都有隐含前提（有网络、参数非空、字段存在）。
>    Bug 几乎都发生在**前提失效**的那一刻。
> 2. **写最小复现把变量降到 1 个**：如果 bug 只在完整链路出现，我会做一个
>    只含必要节点的图，几秒跑完。这样能把「模型发挥不稳定」和「机制问题」分开。
> 3. **用对照实验分离假设**：不要跑一次看结果——**跑三次，每次只改一个变量**。
>
> 记忆模块那两个坑都是这么做出来的。

### C2.（贴代码）这个包装器有什么问题？

```python
def traced(name):
    def decorator(fn):
        def wrapper(state):          # ← 注意签名
            t = time.time()
            result = fn(state)       # ← 没有传 config
            log.info(f"{name} 耗时 {time.time()-t:.1f}s")
            return result
        return wrapper
    return decorator
```

**参考答**：

> **问题：`wrapper` 只接受 `state`，把 LangGraph 注入的 `config` 丢掉了。**
>
> 后果是**静默的**：节点照常执行、功能完全正常，但 `config` 里的 callbacks
> 到不了下游 LLM 调用 → **token 统计归零**，成本监控看起来好好的，实际是瞎的。
>
> 本项目里这个坑出现了**两次**（`utils/tracer.py` 的 `traced` 和
> `graph_2.py` 的 `_traced_router`），第三次差点忘在 `transform_query_node`。
>
> **修法**：显式接收并透传，用 `inspect.signature` 判断原函数是位置参数还是仅关键字参数：
>
> ```python
> def wrapper(state, config=None):
>     ...
>     if _accepts_positional(fn): result = fn(state, config)
>     else:                          result = fn(state, config=config)
> ```
>
> 面试可以补一句：**「第三次是我当时 grep 找漏了——我用变量名 `chain.invoke(` 去搜，
> 而那里变量叫 `question_rewriter`。后来我改成按『调用形状』搜（`\.invoke\(`），
> 再人工过一遍。」**

### C3.（贴代码）为什么这个字段改了不生效？

```python
class Foo(BaseModel):
    k: int = Field(default=MODULE_LEVEL_K)     # ← 类定义时求值

def build():
    return Foo()          # ← 不传 k，永远用类定义时的值
```

**参考答**：见第三部分方法论里的 L3 案例一。核心是**类属性和运行时值是两个时刻**，
`Field(default=...)` 在类定义时就把 `MODULE_LEVEL_K` 的**当前值**抄进去了，后面改模块变量对它无效。

### C4.（贴代码）这段消息累积为什么最后只剩 2 条？

```python
for output in graph.stream(inputs, config=config):
    for node, value in output.items():
        final_state.update(value)      # ← 问题
```

**参考答**：

> `stream()` 产出的是**每个节点的增量**，不是完整 state。
> 图内 `messages` 因为 `add_messages` reducer 累积到 4 条，但 `generate` 节点返回的
> **增量只有本轮新增的 2 条**，`update()` 就把 4 覆盖成 2。
>
> 我是用诊断发现的——**在第二轮前手动 `get_state()` 读一次**：
>
> ```
> [诊断] 第2轮前 get_state 读到 messages=2 条   ← 历史在，checkpointer 对
> 第2轮    messages=2                            ← 但返回值被增量覆盖
> ```
>
> **修法**：记忆模式下改用 `graph.get_state(config).values` 取完整 state。
>
> 一般化教训：**「reducer 字段」和「流式增量」是两个视角，不能混用。**

### C5.（贴代码）这个判据哪里错了？

```python
has_memory = state.get("messages") is not None
```

**参考答**：

> **`LangGraph` 会把 `TypedDict` 里声明的 `messages` 初始化为 `[]`，不是 `None`、也不是「缺失」**，
> 所以这个判据**恒为真**——单轮调用也会被当成记忆模式并往里写历史。
>
> 我用一个只含 `probe` 节点的小图直接验证：`state.get("messages")` 返回 `[]`。
>
> **修法**：用一个「只有记忆模式才会注入」的字段作判据，例如 `bool(state.get("session_id"))`。
>
> 一般化教训：**「字段是否声明」和「字段是否有值」是两回事，框架会替你初始化。**

### C6. 你怎么发现「golden 标错」而不是「模型错了」？

**参考答**（这条证明你有独立判断）：

> n005（召回率最低的产品）连续 10 次拒答，而 golden 块每轮都在上下文里。
> 逐层排除后确认：检索对、判分对、上下文没截断、答案确实在上下文里。
>
> 最后一根稻草是**回库核对原始数据**：我把 85 条召回率记录全量拉出来排序，
> 发现最低是 61.35%，而 golden 标的是 83.52%——golden 取的是「静态向量检索/0% 过滤」
> 那一行，**不是全表最低**。
>
> 所以真实情况是「**模型答 61.35% 是对的，标注错了**」。
> 改标注而不是改模型。后续还发现**表格被切成 4 片导致模型看不到完整表**，
> 这是另一个真 bug，用「同表切片合并」修掉，实测从 3/3 拒答变成 3/3 答对。
>
> **一般化教训：当系统和预期不一致时，先怀疑两边——「标准答案」也是代码写出来的。**

### C7. 缓存不失效的问题怎么查？

（如果面试问「怎么设计缓存」）

**参考答**：给出**已查证无缺陷**的结论，并讲清验证逻辑：

> 项目里有一个 `JudgeCache`，key = `(kind, question, generation, contexts)`。
> 我一度认为它「缺了 golden answer 字段，改了标注缓存不失效」。
>
> 验证办法是**去看每个判定函数实际依赖什么**：
>
> | 函数 | 依赖 | 用 golden 吗 |
> |---|---|---|
> | `judge_faithfulness` | `(documents, generation)` | **不用** |
> | `judge_answer_relevancy` | `(question, generation)` | **不用** |
> | `generate_answer` | `(question, docs)` | **不用** |
>
> key 恰好覆盖了真实依赖，**设计是正确的**——是我的初判错了，我把它标成「已被推翻」。
>
> 一般化：**缓存 key 的判据不是「看起来该有什么」，而是「下游实际读什么」。**

### C8. 模型算不准表格怎么办？（**这题能拉开差距**）

**背景**：n005「召回率最低的产品」稳定答错（89.93% 而非 61.35%）。

**参考答（按排查链讲，不要直接说答案）**：

> 我先分三层排查，**每层都用数据排除**：
>
> 1. **检索**：含 61.35 的块在不在上下文？—— 在（1 块）。
> 2. **合并**：表格是否完整？—— 87 行完整表，**同时含 61.35 和 89.93**。
> 3. **推理**：那为什么还错？—— 加 prompt 引导后从 0/3 到 **1/3**，说明是**模型不做全表比较**。
>
> 结论：**「扫 87 行 × 8 列 ≈ 700 个单元格取最小值」本质是精确计算，是 LLM 的固有弱项**，
> 加提示只能改善不能根治。
>
> **所以我把它交给代码**：新增 `tools/table_query.py`，解析 markdown 表 → 定位「召回率」列
> → 算最小值 → 返回带完整定位的事实文本，注入 prompt 让模型**只需陈述**。
> 效果 **3/3 稳定**。
>
> **关键是降级设计**：算不出来（列不存在/非表格/无聚合词）返回 `None`，
> 自动退回「让模型自己扫」的原路径 —— **不能因为新路径失败就阻断问答**。
>
> 边界也要说清：只处理**单块单列**聚合；跨表联合、多列条件筛选、图表内数值仍未做，
> 那属于 text-to-SQL 范畴。

**为什么这题值钱**：

```
它展示的是「知道 LLM 的能力边界在哪里」——
不是「加更多 prompt」，而是「识别出这是计算问题，就该换工具」
```

## D. AI 协作（差异化最强）

### D1. 你平时怎么用 AI？它写的代码你直接用的吗？

**参考答**：

> 分工是「**我做设计和验证，AI 做实现和样板**」。
>
> 具体到我的验收习惯，有三条硬规则：
>
> 1. **批量/破坏性操作必须 dry-run**：改文件、删数据、批量替换，先跑 dry-run
>    看 10 条样例再 apply。拦下过三次：一次会压扁 13,752 行的目录树对齐，
>    一次会把 `def f():` 改成 `def f:`（破坏 Python 语法但不报错）。
> 2. **结论要证据**：AI 说「reranker 通常提升显著」，我用 8 题 A/B 实测增益为 0，否决。
> 3. **AI 说「这是 bug」时，也可能它错了**：它断言缓存 key 有缺陷，我验证后发现
>    那三个判定函数根本不读那个字段——**AI 错了，我改回了自己的初判**。
>
> 第二条和第三条的**成本对比**：验证 reranker 花 20 分钟，避免了几十小时的无效改造；
> 验证缓存花 5 分钟，避免了一次误改。

### D2. AI 写的代码出错，你怎么发现的？给个具体例子

**参考答**（用 dry-run 那个，最有画面感）：

> 最典型的是正则批量替换。我让它把文档里 169 处日期删掉，它给了四条规则，
> 说「保守、不会误伤」。我每条都先看 dry-run 样例——
>
> | 它的规则 | dry-run 显示的后果 |
> |---|---|
> | `[ \t]{2,} → " "` | 会改 13,752 行，把 `│   ├──` 这种对齐全压扁 |
> | `[（(]\s*[)）] → ""` | 会把**函数调用的空参数列表**也删掉 |
> | `[，,]\s*[。.] → "。"` | 把 `, ...` 变成 `。..` |
>
> 最后我只保留「删日期」这一条，其余全删。**159 倍的改动量差异**（13,752 vs 165）。
>
> 这件事之后我有个原则：**正则规则越界一次，就回退重新设计，不要在上一条上再补一条**。

### D3. 你怎么保证 AI 帮你写的代码质量？

**参考答**：

> 三件事：
>
> ① **实验设计我先写**：比如记忆模块，我先定义「要验证哪 4 条契约」，
>    AI 去实现，我按契约一条条验。**契约由我定义，实现可以外包**。
> ② **最小复现由我写**：把 bug 隔离到不调 LLM、几秒跑完的小用例，
>   这样能分清「机制问题」和「模型波动」。
> ③ **拒绝「通过率」掩护**：我会检查「测试是否真的注册进了回归」——
>    曾经出现过写了测试没注册、以及注册了但输出格式不匹配导致
>    「已运行，无通过率可解析」两次同类问题。**全绿不等于测到了。**

### D4. AI 有没有帮你避免过错误？

**参考答**（有，要说，这才客观）：

> 有。最典型的是 **`traced` 包装器的 config 透传**——我自己重写过一次，
> 觉得「改成 `wrapper(state, config=None)` 就完了」，是 AI 提醒我
> 还有 `_traced_router` 那一路，并且提示「要用 `inspect.signature` 分辨
> 位置参数和仅关键字参数」，否则会 `TypeError`。
>
> 我当时的漏洞：**只 grep 了 node 那一侧，漏了条件边那一侧**。
>
> 这个例子说明我和 AI 的分工是对的——**它做全量扫描，我做价值判断**。

## E. 工程化与评测

### E1. 怎么证明你的改动没让系统变差？

**参考答**：

> 三道闸：
>
> 1. **门禁**：`context_recall ≥ 0.60`、`hit_rate ≥ 0.75`、`faithfulness ≥ 0.60` 等
>    五项，PASS/FAIL 明确。**`context_precision` 我移出了告警集合**（不再刷告警），
>    但**保留 0.03 的硬门禁**——它在宽召回架构下天然低（返回 18 条只为命中 1 条），
>    拿它告警会造成长期误报；但「口径失真」的是告警阈值，不是底线，所以硬门禁留着。
> 2. **回归**：**19 项**，其中 2 项端到端跑图（教训来自 `_cfg` 未定义那次）。
> 3. **A/B 留存**：每次改动的 before/after 报告按题号存档，可复核。
>
> 另外做评测我坚持**确定性指标和 LLM 指标分离**：检索层用块 ID 比对（可复现），
> 生成层用 LLM 判定。混在一起的话，重跑一次数字就变，根本没法比。

### E2. 你说评测代码比业务代码多，值不值？

**参考答**（这题是展示工程品味的好机会）：

> 值。它直接抓到过 5 个我自己的 bug，包括**两次 golden 标错**——
> 如果不改标注，我会把「正确的模型行为」当成缺陷去修，**越改越坏**。
>
> 它还帮我**否掉了三个方案**（reranker、父子块索引、提高相似度门槛）。
> 这三个如果直接做，工作量加起来大概几十小时，而收益是 0 或负。
>
> 但我也想说清楚它的**边界**：32 题样本太少，**单个题就能翻转结论**
> （n005 就是抖动样本）。所以我一件事反复强调：**先测基线自身的抖动，再做 A/B**——
> 否则会把「模型波动」当成「我的改动生效了」。

### E3. 评测怎么保证可比性？

**参考答**：

> 三个机制：
>
> ① **判分缓存**：`(kind, question, generation, contexts)` 做 key，
>    同一输入复用判定结果，消除 LLM 判分抖动。
> ② **异常数入账**：判分失败、判分异常**单独统计**，不混进通过率——
>    曾经因为没统计，把「兜底保留」当成了「召回的功劳」。
> ③ **样本 ID 存档（QIDS）**：一次测量实际覆盖了哪几题写进报告，
>    否则「默认测 3 题」会被当成「测了 6 题」用。

## F. 数据、成本与运维

### F1. 这个项目花了多少 token？怎么优化的？

**参考答**：

> 先说一个反直觉的发现：**优化前的可见成本是假的**。
>
> 真实 41,868 token，监控里只看到 9,898——**4.2 倍的缺口**。
> 根因是 `traced` 包装器把 config 丢了，**判分阶段（占总调用 90%、
> 占真实成本 76%）的 token 完全没被统计**。
>
> 修完之后才看清成本结构，然后做两件优化：
>
> 1. **批量判分**：36 次调用合并成 5 次，token 省 40%（173,265 → 104,378），
>    调用数 215 → 30。**内容一字未改**，只省掉「被重复发送 36 遍的 system prompt」。
> 2. **批间并发**：判分阶段 3.83s → 1.20s。
>
> 端到端 7.2s → 3.8~5.4s。
>
> **经验：成本不可见的系统，优化无从下手。** 另外「大幅降本」往往来自
> 「你已经付过但没意识到的钱」，不是砍功能。

### F2. 生产中要注意什么？

**参考答**：

> 按优先级：① checkpointer 换成 PostgresSaver（SQLite 单文件并发写是瓶颈）；
> ② Milvus 要多副本 + 监控（standalone 没有高可用）；③ LLM 要有限流和降级
> （项目里已经区分「环境不可用」和「逻辑失败」，限额耗尽时**明确报错而不是返回 0 分**）；
> ④ 会话记忆要加 TTL，否则 checkpoints.db 无限增长。
>
> 还有一条与代码无关的：**LLM 余额耗尽的报错是 APITimeoutError 而不是 401**，
> 一开始按「网络问题」排查了半天。**看错误码，不要只看错误类型。**
